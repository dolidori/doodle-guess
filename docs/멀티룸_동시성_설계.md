# Doodle Guess 멀티룸·동시성 설계

## 1. 목적과 근거

이 문서는 여러 방의 격리, 방별 명령 직렬화, 정원 경합, 수명주기, 부하·백프레셔 기준의 단일 설계다.

- 멀티룸: `게임 설명.md` 1~2행
- 약 30명: `게임 설명.md` 3행, 정확한 정원은 `결정_기록.md` D-03
- 최초 정답과 입력 잠금: `게임 설명.md` 4행
- 강퇴·재입장: `게임 설명.md` 13행, D-14~D-16
- 호스트 비이양: `게임 설명.md` 14행
- 30분 호스트 부재 TTL: D-17
- 라운드 제한 시간: `결정_기록.md` D-21
- 서버 재시작 시 소멸: D-18
- 서버 권위·검증: 공통 지침 §1.2, §3.7
- 부하 수치와 일반 참여자 재접속 유예는 게임 설명에 없어 결정한 구현 규칙이다.

## 2. 단일 프로세스 권위 구조

P1 서버는 단일 Node.js 프로세스의 `Map<roomCode, Room>`에 상태를 둔다. DB와 Redis는 사용하지 않는다. 모든 연결은 정확히 한 방 컨텍스트만 가질 수 있다.

```text
WebSocket parse/strict validation/rate limit
  → authenticated connection context
  → RoomCommandQueue(roomCode)
  → permission + phase revalidation
  → atomic state mutation
  → recipient-specific broadcast
```

`JOIN_ROOM`을 제외한 명령의 방은 payload가 아니라 서버의 연결 컨텍스트로 결정한다. 발신자가 보낸 역할·playerId·drawerId는 받지 않는다. 방 브로드캐스트는 Room의 현재 연결 Set을 직접 순회하며 전역 소켓 목록을 필터링하지 않는다.

## 3. 방번호와 정원

- 방번호는 문자열 정규식 `^[1-9][0-9]{2}$`, 범위 `100~999`다.
- 생성은 CSPRNG로 후보를 뽑고 Room Map에 없는지 같은 이벤트 루프 tick에서 검사·삽입한다.
- 32회 충돌하면 100부터 순회해 빈 번호를 찾는다. 900개가 모두 사용 중이면 `ROOM_CODE_EXHAUSTED`.
- 정원은 논리 플레이어 슬롯 30명이다. 호스트와 진행자를 포함하며 재접속 유예 중 `connected:false` 슬롯도 포함한다.
- 마지막 자리의 동시 JOIN은 방 큐에서 처리한다. N-1 상태의 여러 요청 중 큐에서 처음 실행된 하나만 성공한다.
- 진행 중인 슬롯 복구는 새 슬롯을 사용하지 않는다.

## 4. 방별 FIFO 명령 큐

방 상태를 바꾸는 모든 명령은 하나의 FIFO 큐를 지난다.

- 입장·퇴장·disconnect 처리
- 제시어 확정과 라운드 시작
- 추측 수락과 정답 확정
- stroke batch·undo·clear
- drawer 지정·회수
- 강퇴
- 다음 라운드 준비
- round deadline 만료
- 호스트 TTL 만료

JSON 파싱, strict 스키마, 메시지 크기, 연결별 Rate Limit은 enqueue 전에 수행한다. 권한·멤버십·현재 phase·round/revision/epoch 검증은 반드시 큐에서 실행 직전에 다시 수행한다.

큐 길이 상한은 200개다. 초과 시 새 명령은 `SERVER_BUSY`로 거부한다. 수락 명령의 처리 시간 목표는 5ms 이하, 큐 대기 p95는 50ms 이하다. drawing batch도 같은 큐를 사용하되 초당 25개 제한으로 제어 명령 기아를 막는다.

## 5. 경합별 원자 규칙

### 5.1 최초 정답

1. `SUBMIT_GUESS`를 방 큐 순서로 실행한다.
2. 자격·phase·잠금·문자열을 검증한다.
3. 수락된 추측에 다음 `guessSeq`를 부여하고 공개 feed에 기록한다.
4. `GUESS_SHARED`를 방 전체에 보낸다.
5. 정답이면 같은 큐 작업 안에서 `status=SOLVED`, `guessLocked=true`, winner를 한 번 기록하고 `ROUND_SOLVED`를 보낸다.
6. 이후 실행되는 추측은 `ROUND_LOCKED`로 거부하며 공개 feed에 넣지 않는다.

“최초”는 클라이언트 시각이 아니라 서버가 해당 방 큐에 넣은 순서다.

### 5.2 권한 변경과 stroke

`ASSIGN_DRAWER`/`RECLAIM_DRAWER`가 실행될 때 `drawerEpoch`을 증가시킨다. 그 뒤 실행되는 이전 epoch batch는 `STALE_DRAWER_EPOCH`이다. 변경 전에 수락된 벡터는 D-12에 따라 유지한다.

### 5.3 Clear·undo와 stroke

undo는 실행 순간의 마지막 확정 stroke 하나만 제거한다. clear는 `drawingRevision`을 증가시키고 벡터를 비운다. clear 뒤 큐에 남은 이전 revision batch는 모두 거부한다.

### 5.4 강퇴와 대상 명령

강퇴가 먼저 실행되면 대상의 Room membership과 session token을 즉시 무효화하고 이후 큐 명령은 `NOT_IN_ROOM`으로 거부한다. 대상 명령이 먼저 실행됐으면 그 결과까지는 유효하다. 강퇴 대상의 닉네임과 token hash는 방 수명 동안 ban Set에 둔다.

호스트와 진행자는 강퇴 대상이 될 수 없다. 호스트 또는 진행자만 일반 참여자를 강퇴할 수 있다.

### 5.5 다음 라운드와 지연 이벤트

`START_NEXT_ROUND`는 새 `roundId`와 `drawingRevision`을 만들고 guess/drawing 상태를 초기화한다. 이전 roundId의 guess와 stroke는 각각 `STALE_ROUND`로 거부한다.

### 5.6 정답과 제한 시간 만료

`SET_KEYWORD_AND_START`가 성공한 서버 시각에 `roundEndsAt`을 계산한다. timer callback은 상태를 직접 바꾸지 않고 캡처한 `roundId`와 함께 `EXPIRE_ROUND` 내부 명령을 Room 큐에 넣는다.

- 실행 시 roundId, 활성 status, 현재 서버 시각을 다시 검사한다.
- callback이 일찍 실행되면 남은 시간만큼 다시 예약한다.
- deadline 이후 큐에서 실행되는 guess·stroke·undo·clear는 expiry 명령보다 먼저 enqueue됐더라도 서버 시각 검사로 거부한다.
- 정답 처리가 먼저 실행되어 `ROUND_SOLVED` 상태가 되면 round timer를 취소하고 뒤의 expiry 명령은 폐기한다.
- expiry가 먼저 실행되면 그림과 추측을 원자 잠그고 안정된 eventId의 `ROUND_EXPIRED`를 한 번 브로드캐스트한다. 뒤의 정답·그림 요청은 거부한다.
- 다음 라운드, Room close에서도 이전 timer를 취소한다. 남은 callback은 roundId guard로 현재 라운드를 변경할 수 없다.

## 6. 공개·비공개 팬아웃

- `PUBLIC_STATE`, `GUESS_SHARED`, `ROUND_SOLVED`, drawing delta는 현재 방 연결에만 보낸다.
- `PRIVATE_STATE`는 수신자별로 새 객체를 만들어 보낸다. keyword는 현재 drawer와 진행자에게만 포함한다.
- 권한이 회수된 drawer에게 보내는 이후 PRIVATE_STATE에는 keyword가 없다.
- 서버 로그에는 keyword, 정규화 정답, session token을 쓰지 않는다.
- 공개 추측은 최근 100개만 Room 메모리에 보존해 재접속자에게 복원한다. 거부된 입력은 공개·보존하지 않는다.

## 7. 연결 종료와 Room 수명

### 7.1 일반 참여자

- 예기치 않은 disconnect: `connected=false`로만 바꾸고 슬롯·역할·keyword 열람 이력을 방이 닫힐 때까지 유지한다.
- session token 또는 연결 끊긴 동일 닉네임으로 복구하면 같은 슬롯을 되살린다.
- 다른 닉네임은 즉시 새 슬롯이며 기존 끊김 슬롯을 소비하지 않는다.
- 명시적 `LEAVE_ROOM`은 즉시 슬롯을 제거한다.

### 7.2 호스트

- disconnect 시 `isHost`, `drawerId`, 슬롯을 유지하고 절대 자동 이양하지 않는다.
- 호스트 부재 타이머는 disconnect 처리와 같은 큐 작업에서 30분으로 설정한다.
- 원 session token 또는 연결 끊긴 정확히 같은 닉네임으로 복구하면 타이머를 취소한다. 이미 연결된 호스트 닉네임 입장은 거부한다.
- 30분 만료도 큐에 넣어 재접속과 순서를 결정한다. 만료가 먼저 실행되면 `ROOM_CLOSED(HOST_ABSENT_TIMEOUT)`을 연결자에게 보내고 방을 삭제한다.
- 호스트가 명시적으로 나가면 즉시 `ROOM_CLOSED(HOST_LEFT)` 후 방을 삭제한다.
- 호스트 부재 중 활성 라운드의 일반 추측은 계속 가능하다. 연결된 drawer가 있으면 그리기도 계속 가능하다. 일반 모드의 다음 라운드 준비와 호스트 전용 관리는 중단된다. 진행자 모드에서 host 겸 moderator가 부재하면 동일하게 중단된다.

### 7.3 서버 재시작

D-18에 따라 Room은 복구하지 않는다. 재기동 뒤 이전 방번호 JOIN은 `ROOM_NOT_FOUND`다. 클라이언트는 이를 명시적으로 표시하고 새 방 생성으로 안내한다.

## 8. Heartbeat와 정리

- 서버는 45초마다 WebSocket ping control frame을 보낸다.
- 직전 ping 이후 pong이 없고 90초가 지나면 연결을 종료해 disconnect 큐 작업을 실행한다.
- visibility 복귀 시 클라이언트는 연결 상태를 검사하고 닫혔으면 session token으로 재접속한다.
- Room 타이머, 연결 Set, rate bucket, dedupe cache는 Room 삭제와 함께 모두 해제한다.
- dedupe 키는 해당 drawing revision이 끝나거나 Room이 삭제될 때 폐기한다.
- round timer는 Room당 최대 하나다. `SET_ROUND_DURATION`은 준비 상태에서만 20~180 정수·5초 배수로 바꾸며 활성 상태에서는 timer와 값을 모두 변경하지 않는다.

## 9. Rate Limit과 메시지 상한

토큰 버킷은 연결별이며 CREATE/JOIN은 IP별 보조 버킷도 적용한다.

| 이벤트군 | 지속 허용 | burst | 최대 메시지 |
|---|---:|---:|---:|
| `CREATE_ROOM`, `JOIN_ROOM` | 분당 5회/IP | 5 | 2KiB |
| `LEAVE_ROOM` | 초당 2회 | 2 | 1KiB |
| `SET_KEYWORD_AND_START` | 10초당 2회 | 2 | 1KiB |
| `SET_ROUND_DURATION` | 10초당 5회 | 5 | 1KiB |
| `SUBMIT_GUESS` | 초당 4회 | 8 | 1KiB |
| `DRAW_STROKE_BATCH` | 초당 25회 | 40 | 8KiB |
| `UNDO_LAST_STROKE`, `CLEAR_DRAWING` | 초당 3회 | 5 | 1KiB |
| drawer·kick·next-round 제어 | 10초당 5회 | 5 | 1KiB |

모든 C→S JSON의 절대 상한은 16KiB다. 초과 프레임은 1009로 종료한다. 개별 이벤트 상한 초과는 `PAYLOAD_TOO_LARGE`, bucket 초과는 `RATE_LIMITED`이며 상태를 바꾸지 않는다.

## 10. 백프레셔와 장애 격리

연결별 `bufferedAmount`가 256KiB 이상이면 해당 느린 연결에 drawing delta를 보내지 않고 snapshot-required로 표시한다. 128KiB 미만으로 회복하면 최신 vector snapshot을 64KiB 이하 청크로 보낸다. 1MiB 이상이 5초 지속되면 1013으로 종료한다.

한 연결의 send 오류는 그 연결만 disconnect 처리한다. broadcast loop를 중단하거나 다른 방·연결을 기다리지 않는다. Room 큐 예외는 해당 명령을 `INTERNAL_ERROR`로 종료하고 구조화 로그에 roomCode, event type, requestId만 남긴다.

## 11. 부하 목표

정원은 호스트·진행자를 포함한 30명이다.

### 기준 부하

- 20개 방 × 30 연결 = 600 WebSocket
- 방마다 drawer 1명이 초당 20 batch
- 초당 약 400 inbound drawing batch
- 발신자 echo를 포함해 초당 약 12,000 room-local delivery
- 각 참여자가 초당 1회 추측하는 10초 burst

### 스트레스 부하

- 50개 방 × 30 연결 = 1,500 WebSocket
- 초당 약 1,000 inbound drawing batch
- 초당 약 30,000 room-local delivery
- 30분 지속
- 방마다 느린 관찰자 1명 추가 시뮬레이션은 30명 안에 포함

### 합격 기준

| 지표 | 기준 |
|---|---:|
| stroke 서버 수신→정상 관찰자 | p95 ≤150ms, p99 ≤300ms |
| 정답 서버 수신→`ROUND_SOLVED` | p95 ≤200ms, p99 ≤400ms |
| Room 큐 대기 | p95 ≤50ms |
| event-loop lag | p95 <50ms |
| CPU | 30분 평균 <70% |
| RSS 추세 | 워밍업 후 30분 증가율 <10% |
| 정상 연결 누락·중복 | 0 |
| 방 간 유출 | 0 |
| 최초 정답자 수 | 라운드마다 정확히 1 |
| 느린 연결 영향 | 정상 연결 p95 악화 <20% |

절대 CPU·RSS 용량은 배포 인스턴스 사양에 종속되므로 위 테스트 결과와 함께 인스턴스 사양을 기록한다.

## 12. 필수 동시성 테스트

1. 정원 29명 방에 JOIN 50개를 동시에 보내 정확히 1개만 성공한다.
2. 30명이 같은 정답을 동시에 제출하는 시험을 100회 반복해 winner가 매회 하나다.
3. A/B 두 방에서 동일한 ID와 순번을 사용해도 이벤트 유출이 0이다.
4. drawer 변경·clear·stroke batch를 무작위 교차해 stale epoch/revision 수락이 0이다.
5. kick와 대상 guess/stroke를 교차해 kick 실행 뒤 수락이 0이다.
6. 호스트 disconnect/reconnect를 1,000회 반복해 다른 사용자의 `isHost` 승격이 0이다.
7. 호스트 TTL 만료와 재접속을 같은 시각에 enqueue해 FIFO 결과가 일관된다.
8. 1,500 연결 30분 시험에서 큐·메모리·지연 기준을 모두 충족한다.
9. solve와 expiry를 같은 deadline 경계에서 경합시켜 FIFO winner만 상태를 확정하고 `ROUND_SOLVED`와 `ROUND_EXPIRED`가 함께 발생하는 경우가 0인지 확인한다.
10. 이전 라운드 timer callback을 강제로 지연시킨 뒤 다음 라운드를 시작해도 새 라운드 상태가 바뀌지 않는지 확인한다.
