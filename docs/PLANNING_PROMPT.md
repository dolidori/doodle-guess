## 게임 개요

Doodle Guess(가칭)는 여러 방을 동시에 운영할 수 있는 **실시간 그림 맞히기 파티게임**입니다.

- 한 사용자가 3자리 방번호의 방을 개설하고, 방마다 약 30명이 참여할 수 있습니다.
- 일반 모드에서는 방장(호스트)이 제시어를 입력하고 그림을 그립니다.
- 다른 참여자들은 같은 그림을 실시간으로 보며 제시어를 입력해 맞힙니다.
- 띄어쓰기 유무는 정답 판정에 영향을 주지 않습니다.
- 서버가 가장 먼저 도착한 정답을 확정하면 추측 입력을 잠그고, 정답자 닉네임을 모달로 알립니다.
- 진행자 모드에서는 진행자가 그릴 사람을 지정하거나 그리기 권한을 다시 가져올 수 있습니다.
- 그리기 권한을 받은 사람은 제시어 입력과 그림 그리기가 활성화됩니다.
- 제시어는 현재 그리기 권한자와 진행자에게만 공개됩니다. 제시어 옆에는 화면에서 가릴 수 있는 버튼이 있습니다.
- 호스트 또는 진행자는 참여자를 내보낼 수 있습니다.
- 일반 참여자는 연결이 끊긴 뒤 같은 닉네임 또는 다른 닉네임으로 곧바로 다시 접속할 수 있습니다.
- 호스트의 연결이 끊겨도 권한은 이양되지 않으며, 원래 호스트 닉네임으로 재접속하면 호스트 권한을 유지합니다.
- 그림은 전송량을 줄일 수 있도록 비트맵 프레임이 아니라 **벡터 스트로크**로 동기화합니다.

## 반드시 지켜야 할 핵심 불변식

계획 산출물은 아래 불변식을 상태 모델, 이벤트 계약, 서버 검증, 테스트에 각각 반영해야 합니다.

1. **방 격리**: 한 방의 플레이어·제시어·그림·추측·모달 이벤트가 다른 방으로 유출되지 않습니다.
2. **단일 활성 그리기 권한**: 한 방에는 동시에 한 명만 그릴 수 있습니다.
3. **서버 권위 권한 판정**: 클라이언트에서 버튼을 숨기는 것만으로 권한을 보호하지 않습니다. 서버가 모든 그리기·제시어·위임·강퇴 요청의 권한을 검증합니다.
4. **제시어 비공개**: 제시어는 현재 그리기 권한자와 진행자에게만 PRIVATE 상태로 전송합니다. 일반 추측자에게는 DOM이나 PUBLIC 상태를 포함해 아예 전송하지 않습니다.
5. **최초 정답자 단일 확정**: 동시에 여러 정답이 도착해도 서버가 직렬화해 정확히 한 명만 정답자로 확정합니다.
6. **정답 후 입력 잠금**: 정답 확정 뒤에는 해당 라운드의 추가 추측을 서버와 클라이언트 양쪽에서 거부합니다.
7. **띄어쓰기 무시**: 최소한 모든 공백 문자를 제거한 값으로 제시어와 추측을 비교합니다. 그 밖의 정규화는 별도 결정 없이는 추가하지 않습니다.
8. **호스트 권한 비이양**: 호스트 연결이 끊겨도 다른 참여자에게 자동 이양하지 않습니다.
9. **호스트 권한 복구**: 원래 호스트 닉네임으로 재접속하면 기존 호스트 슬롯과 권한을 복원합니다.
10. **벡터 기반 동기화**: 그림의 권위 데이터는 정규화 좌표를 가진 벡터 스트로크이며, 캔버스 전체 이미지를 매 입력마다 전송하지 않습니다.
11. **강퇴 권한 제한**: 호스트 또는 진행자만 참여자를 내보낼 수 있습니다.

### 권장 상태 머신 출발점

아래는 설계 출발점이며 원문에 없는 세부는 대표님 확인 후 확정해야 합니다.

```text
방(Room)
WAITING
  → ROUND_ACTIVE
  → ROUND_SOLVED
  → ROUND_ACTIVE (다음 라운드)
  → CLOSED

연결(Connection)
CONNECTED ↔ DISCONNECTED

라운드(Round)
PREPARING_KEYWORD
  → DRAWING_AND_GUESSING
  → SOLVED
```

방 상태와 연결 상태를 섞지 마세요. `ROUND_ACTIVE` 중에도 개별 사용자는 연결이 끊길 수 있습니다. 각 상태별 허용 이벤트, 전이 주체, 전이 조건, 거부 코드, 재접속 복원 화면을 표로 작성하세요.

### 정답 판정과 경합

- 서버가 제시어의 정규화 값을 보관하고 추측을 서버에서 판정합니다.
- 필수 정규화는 JavaScript의 단순 ASCII 공백 한 칸이 아니라 모든 공백 문자를 제거하는 규칙으로 테스트합니다.
- 동시에 도착한 추측은 방별 명령 큐 또는 동등한 원자적 처리로 순차 판정합니다.
- 최초 정답 처리에서 `round.status = SOLVED`, `winnerId`, `winnerNickname`, `solvedAt`을 한 번만 기록합니다.
- 상태가 `SOLVED`로 바뀐 뒤 도착한 추측은 일관된 오류 코드로 거부합니다.
- 정답 이벤트는 해당 방에만 브로드캐스트하고, 클라이언트는 추측 입력을 즉시 비활성화한 뒤 정답자 모달을 한 번만 표시합니다.
- 이벤트 `seq` 또는 `roundId`를 사용해 재접속·중복 메시지로 모달이 반복되지 않게 설계합니다.

### 호스트 연결 끊김과 재접속

- 호스트가 끊기면 `connected=false`로 유지하고 **자동 이양 함수를 호출하지 않습니다**.
- 원래 호스트 닉네임의 재접속을 기존 호스트 슬롯에 연결하고 `isHost`를 유지합니다.
- 호스트 부재 중 일반 참여자가 할 수 있는 행동과 새 라운드 시작 가능 여부를 명시합니다.
- 일반 참여자는 같은 닉네임으로 기존 슬롯에 복귀하거나 다른 닉네임으로 새로 입장할 수 있어야 합니다.
- 중복 닉네임, 이미 연결된 닉네임 탈취, 강퇴 직후 재입장, 다중 탭 경합을 별도 테스트합니다.
- 게임 설명의 닉네임 기반 복구를 지키면서도 사칭 위험을 줄일 수 있는 세션/복구 토큰 병행안을 제시하고 대표님 결정을 받습니다.

## 제시어 정보 경계

- PUBLIC 상태에는 `hasKeyword`, 라운드 상태 등 화면 구성에 필요한 정보만 포함하고 제시어 원문이나 정답 정규화 값은 넣지 않습니다.
- PRIVATE 상태는 서버가 수신자별로 생성합니다.
- 현재 그리기 권한자와 진행자에게만 제시어 원문을 전송합니다.
- 일반 참여자, 퇴장된 사용자, 다른 방 사용자에게는 제시어를 전송하지 않습니다.
- 제시어 보기/가리기 버튼의 상태와 접근성 라벨을 설계합니다.
- 권한이 회수된 사용자가 이후 PRIVATE_STATE에서 제시어를 받지 않도록 보장합니다. 이미 본 제시어를 되돌릴 수 없다는 한계와 라운드 중 권한 재지정 정책도 명시합니다.
- 로그, 오류 메시지, 분석 이벤트에 제시어가 노출되지 않도록 합니다.

## 실시간 벡터 캔버스 설계

다음 항목을 구현 가능한 수준으로 확정하세요.

- Pointer Events 기반 마우스·터치·펜 입력과 `touch-action: none`
- 입력 중 점 샘플링/단순화, 배치 주기, 한 배치·스트로크·라운드의 최대 크기
- 클라이언트 미리보기와 서버 확정 스트로크의 구분
- `strokeId`와 배치 순번으로 중복·누락·순서 뒤바뀜 처리
- 느린 클라이언트와 서버 백프레셔 처리
- 새 참여자와 재접속자에게 현재 그림 스냅샷을 보내는 방식
- 그리기 권한 변경 순간의 미완성 스트로크 처리
- 권한이 없는 사용자의 스트로크, 과도한 좌표, NaN/Infinity, 캔버스 범위 밖 좌표 거부

- 진행자의 권한 지정·회수와 호스트/진행자 강퇴
- 호스트 권한 자동 이양이 발생하지 않음
- 같은/다른 닉네임 재입장과 호스트 닉네임 복구
- 정규화 벡터 스트로크의 기기 독립 재현
- 재접속 시 현재 그림·라운드·권한 UI 복원
- 여러 탭의 독립 플레이어 세션
- 스트로크 크기·Rate Limit·백프레셔
- 모바일 캔버스 제스처와 Safe Area
- PWA 설치와 아이콘
- §6.3 Tier 1의 프로젝트별 적용 판정

## 최종 검증 체크리스트

### 1. 규칙 정확성

- 게임 설명의 14개 요구가 모두 추적됨
- 릴레이·그룹·타이머·랜덤 제시어 등 다른 게임 규칙이 남아 있지 않음
- 원문에 없는 결정이 `결정_기록.md`에 모이고 대표님 확인을 받음
- 일반 모드와 진행자 모드의 역할·권한이 모순 없이 정의됨
- 호스트 비이양과 재접속 복구가 테스트 가능한 문장으로 정리됨

### 2. 정보 보안과 서버 권위

- 제시어가 권한자별 PRIVATE 상태로만 전달됨
- 다른 방 데이터가 이벤트·스냅샷·로그에서 격리됨
- 서버가 drawer, moderator, host, round 상태를 모두 검증함
- 정답 최초 1인 확정과 입력 잠금이 원자적으로 처리됨
- 강퇴·권한 위임·캔버스 초기화 경합이 정의됨

### 3. 구현 가능성

- 이벤트 계약만 보고 서버와 클라이언트를 독립 구현할 수 있음
- 모든 상태에서 `allowedActions`와 복원 UI를 계산할 수 있음
- 벡터 스트로크가 크기 독립적으로 재현됨
- 약 30명과 여러 방을 검증할 부하 테스트 기준이 수치화됨
- 재접속·권한·정답 경합 테스트 케이스가 구체적임

### 4. 범위 통제

- P1과 P2가 분리됨
- 게임 설명에 없는 점수제·제한 시간·AI·계정·랭킹이 들어가지 않음
- 미정 기능을 구현 편의를 이유로 임의 확정하지 않음
- 모든 변경이 실시간 그림 맞히기 게임 구현에 직접 필요함
